# 포트폴리오를 사이드 프로젝트로 다시 만들기 (1) 기획

> 초안. 사용자가 다듬어 티스토리에 게시할 원고. `[다듬기]` 표시는 본인 경험이나 의견으로 채울 부분.

## 왜 다시 만드나

GitHub Pages에 올려 둔 개인 사이트는 Jekyll Agency 템플릿을 받아 테마만 바꾼 상태로 몇 년째 그대로였다. 2014년 날짜의 샘플 프로젝트 여섯 개가 포트폴리오 자리를 차지하고 있었다.

처음에는 이력서와 경력기술서를 웹으로 옮기는 정도로 생각했다. 정적 HTML로 한 번 만들어 보니 내용은 정리됐지만 PDF를 웹에 띄운 것과 다르지 않았다. 10년 차를 바라보는 프론트엔드 개발자의 사이트라면, 사이트 자체가 작업물이어야 한다는 결론.

[다듬기] 처음 정적 버전을 보고 든 생각, 기준을 바꾸게 된 계기.

## 목표

- 보여 주는 페이지가 아니라 할 수 있는 것을 직접 만져 볼 수 있는 공간
- 지연 없이 깔끔한 애니메이션
- 높은 Lighthouse 점수, 그리고 그 점수를 CI에서 계속 지키기
- SEO와 GEO(생성형 AI 검색 대응)
- 말장난이 아닌 이스터 에그 유머. 크롬 공룡 게임처럼 발견하는 재미
- 주력 기술인 React로 만들기
- 기획과 진행 과정을 블로그에 남기기 (이 글)

## 하지 않기로 한 것

- 회사 제품 화면 캡처와 영상 공개. 저장소가 공개이므로 실제 화면 대신 직접 그린 도식과 데모로 설명
- 전화번호, 고객사명, 이슈와 커밋 번호
- 근거가 충돌하는 수치. 경력 정리 과정에서 자료마다 값이 다른 수치는 싣지 않음
- 기능 수를 늘리기 위한 데모. 각 데모는 실제 경력의 판단 하나와 연결

## 이스터 에그는 경력과 연결

말장난 대신, 실제로 해 온 일을 사이트의 동작으로 만들기로 함.

- **이 사이트는 실행 취소가 된다.** PlotPlan 에디터에서 모든 편집을 command(do/undo)로 통과시킨 구조를 사이트 전체에 적용. 테마를 바꿔도 ⌘Z로 되돌릴 수 있음
- **첫 화면의 미니 에디터.** 장비를 끌면 화면 상태만 바뀌고, 놓는 순간 command 하나로 document에 반영
- **render 2,340회 → 1회 데모.** 장비를 누르면 다시 렌더링된 노드가 깜빡이고, 구독 방식을 바꿔 차이를 직접 확인
- **콘솔 인사.** 개발자 도구를 연 사람에게만 보이는 메시지
- 다음 단계: 일부러 나쁜 UX(레이아웃 이동)로 시작해 스스로 고쳐지는 장면, Service Worker로 오프라인일 때 뜨는 미니 게임

## 정보 구조

- `/` 첫 화면: 이름과 한 줄 소개, 미니 에디터, 대표 사례 5개, 이 사이트에 대한 설명, 경력, 기술, 연락
- `/work/plotplan`, `/work/chipnsoda`, `/work/miridih` 사례 상세: 문제 → 구조 판단 → 변경 → 측정 → 남은 과제
- `/system` 디자인 시스템: 이 사이트를 만든 토큰과 컴포넌트를 실제로 렌더링

채용 담당자는 첫 화면을 1분 안에 훑고, 면접관은 사례 상세를 깊게 읽는다는 가정. 그래서 첫 화면은 짧게, 상세는 길게.
